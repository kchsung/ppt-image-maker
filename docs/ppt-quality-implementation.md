# PPT 구성 및 품질 적용 현황

이 문서는 QLEARN PPT Maker에 현재 적용된 기획, 구성, 편집 가능 출력, 품질 검증 방식을 정리한다. 대상 경로는 `/ppt-maker`이며, 결과물은 이미지 슬라이드가 아닌 **편집 가능한 텍스트·도형·표·차트·도식 객체로 구성된 PPTX**다.

## 1. 현재 제작 원칙

PPT는 단순히 입력 문장을 요약해 카드에 배치하지 않는다. 다음 순서로 제작한다.

1. 요청과 첨부자료를 분석해 발표 조건을 구조화한다.
2. 전체 덱의 논리와 목차를 먼저 설계한다.
3. 섹션별로 장표 문구와 장표 역할을 생성한다.
4. 내용의 성격에 맞는 레이아웃을 배정한다.
5. 같은 HTML/CSS 장표를 화면 미리보기와 PPTX 변환에 함께 사용한다.
6. 텍스트·도형·표·차트·도식을 편집 가능한 PowerPoint 객체로 내보낸다.
7. 내보내기 전후에 문구, 밀도, 가독성, 정렬, 출처, 디자인 기준을 검사한다.

새 덱은 OpenAI 이미지 생성, Claude PPT 재생성, Netlify 장기 워커에 의존하지 않는다. 이전 이미지 기반 프로젝트는 조회만 가능하며, 새 생성 흐름의 품질 기준에는 포함하지 않는다.

## 2. 입력 분석과 필수정보 보완

`analyze-ppt-request`는 사용자가 입력한 주제, 목적, 청중, 발표 시간, 장표 수, 문서 유형, 핵심 메시지, 지시사항을 분석한다.

- **요청 분석**: 주제, 목적, 청중, 권장 장표 수, 발표 시간, 문서 유형, 발표 형식을 추출한다.
- **목적별 기본 구성**: IR/투자덱, 사업제안서, 회사소개서, 결과보고서, 교육자료, 전략·의사결정, 실행 로드맵에 따라 기본 목차와 결론 형식을 달리 적용한다.
- **필수정보 보완**: 목적, 청중, 분량, 스타일, 세부 내용이 불명확하면 선택형 질문을 반환한다. 답변은 요청에 저장되고, 완성 전에는 계획 생성을 시작하지 않는다.
- **내용 밀도**: `Light`는 장표당 3개, `Standard`는 4개, `Detailed`는 5개의 근거 블록을 요구한다. `Detailed`는 문장을 무작정 늘리는 방식이 아니라 주장·근거·영향·실행 조건을 분리해 설명한다.
- **추가 지시사항**: 반드시 포함할 메시지, 제외할 표현, 말투, 의사결정 요청, 근거 요구사항을 계획 프롬프트에 그대로 전달한다.

## 3. 첨부자료와 출처

입력 화면은 텍스트 외에 PDF, DOCX, PPTX, XLSX, PNG, JPEG, WEBP를 최대 8개까지 받는다.

- 문서와 표 파일에서는 본문, 핵심 문장, 데이터 후보를 추출한다.
- 이미지는 요청 분석 시 시각적 참고자료로 사용한다.
- 첨부파일명, 본문 URL, 발행연도 정보를 바탕으로 출처 레지스트리를 구성한다.
- 수치·사실을 담은 장표는 등록된 출처 ID를 연결해야 한다.
- PPTX의 하단에는 간결한 출처 라벨을 넣고, 상세 출처명·문서명·연도·URL·확인일은 결과 패널에서 확인한다.

출처가 없는 숫자나 확인할 수 없는 사실을 새로 만들어 내보내지 않는 것이 원칙이다.

## 4. 전체 덱 기획과 장표 의존관계

### 덱 블루프린트

`generate-ppt-deck-blueprint`가 모든 장표를 한 번에 쓰기 전에 전체 청사진을 만든다.

- 핵심 주장, 청중의 필요, 최종 기대 결과
- 도입 → 근거 축적 → 행동 요청의 서사 구조
- 섹션명, 섹션 역할, 청중의 핵심 질문, 장표 범위, 장표 수, 시각 방향
- 목적별 필수 목차와 결론 형식

각 섹션은 최대 10장으로 제한한다. 따라서 50장은 5개, 100장은 10개 이상의 독립적이지만 연결된 섹션 작업으로 나뉜다.

### 섹션 단위 Slide JSON

`generate-ppt-slide-plan`은 일반 규모의 덱에서 최대 두 요청까지 병렬로 만든다. 다만 `Detailed` 밀도 또는 21장 이상 덱은 OpenAI의 분당 토큰 한도를 보호하기 위해 한 섹션씩 순차 계획한다. 429 응답은 서버와 브라우저 모두 `Retry-After` 또는 오류 본문의 대기 시간을 읽어 제한된 백오프로 재시도한다. 섹션은 공통 블루프린트와 앞 섹션의 요약 핸드오프를 받아, 병렬 처리 중에도 전체 논리를 유지한다.

각 장표에는 아래 정보를 저장한다.

- 장표 역할: 표지, 맥락, 문제 제기, 근거, 비교, 해결방안, 실행, 사례, 의사결정, 결론 중 하나
- 메시지형 제목, 목적, 핵심 메시지
- 3~5개의 근거 블록: `heading`과 완결된 `detail`
- 핵심 시사점과 다음 행동 또는 의사결정 요청
- 앞 장표가 남긴 질문, 현재 장표가 답하는 질문, 다음 장표로 넘길 질문
- 레이아웃 후보와 시각 방향
- 출처 ID

이 구조로 단순 주제형 제목, 중복 장표, 결론 없는 목차 나열을 차단한다.

## 5. 레이아웃과 디자인 시스템

### 레이아웃 선택

콘텐츠 성격을 기준으로 다음 구조를 선택한다.

- `hero-visual`: 표지 또는 핵심 주장
- `message-emphasis`: 한 문장 결론 강조
- `card-grid`: 핵심 요소 묶음
- `side-by-side-comparison`: 두 대안·현재/목표 비교
- `numbered-process`: 실행 단계·절차
- `before-after-mapping`: 변화 전후
- `hub-and-spoke`: 관계·운영 모델
- `metrics-dashboard`: 핵심 수치·KPI
- `roadmap`: 일정·마일스톤
- `pyramid-framework`: 계층·성숙도·우선순위
- `case-story`: 사례와 효과
- `closing-commitment`: 결론·의사결정 요청

인접 장표에 같은 레이아웃이 반복되지 않도록 하고, 장표 수에 따라 필요한 최소 레이아웃 다양성을 검증한다. 선택한 디자인 템플릿은 색상 토큰과 추천 시각 구조를 제공하지만, 모든 장표를 같은 카드형으로 강제하지 않는다.

### 공통 디자인 규칙

- 16:9 슬라이드와 12열 기준 그리드를 사용한다.
- 안전 여백, 헤더, 본문, 하단선, 페이지 번호 영역을 고정한다.
- 선택 템플릿의 주색·강조색·서피스 색을 편집형 레이아웃에 적용한다.
- 로고가 없으면 우측 상단에 편집 가능한 `로고` 자리표시자를 둔다.
- 로고가 있으면 같은 위치에 업로드한 로고를 넣는다.
- 모든 생성 텍스트는 Pretendard 계열을 지정한다.

## 6. 편집 가능한 PPTX 출력

`PptHtmlSlide.tsx`는 Slide JSON을 HTML/CSS로 렌더링한다. 이 컴포넌트는 화면 미리보기와 숨겨진 내보내기 DOM에서 동일하게 사용된다.

1. 사용자는 브라우저에서 최종 슬라이드와 같은 화면을 본다.
2. `dom-to-pptx`가 같은 DOM의 텍스트, 카드, 표, 도식, 커넥터를 PowerPoint 객체로 변환한다.
3. 브라우저가 만든 PPTX 바이너리는 짧은 Supabase Storage 저장 요청으로 업로드한다.

따라서 최종 PPTX는 슬라이드 전체 이미지를 붙인 결과가 아니라, 텍스트와 대부분의 도형을 PowerPoint에서 편집할 수 있는 결과물이다. `PptxGenJS`는 명시적 폴백, 특수 객체, 수동 추가 장표의 보조 경로로 유지한다.

## 7. 자동 품질 게이트

다음 기준을 통과해야 내보내기 가능한 덱으로 취급한다.

| 구분 | 검증 기준 |
| --- | --- |
| 문구 | 빈 값, 말줄임표, 대체 문자, 자리표시자, 대상 언어와 다른 문구, 주제형 제목, 중복 메시지를 검사 |
| 논리 | 도입-근거-행동 구조, 장표 역할, 앞뒤 질문 연결, 마지막 장표의 결론 완결성을 검사 |
| 목차 | 요청 장표 수가 섹션 범위에 한 번씩만 배정되는지, 섹션 역할과 청중 질문이 있는지 검사 |
| 밀도 | Light/Standard/Detailed별 근거 블록 수와 상세 설명 유무를 검사 |
| 출처 | 출처 레지스트리가 있는 경우 수치·사실 장표에 출처 ID가 있는지 검사 |
| 레이아웃 | 반복 구조, 장표 역할과 레이아웃의 불일치, 패널 개수와 배치 오류를 검사 |
| 텍스트 | 글상자 범위, 겹침, 하단 침범, 최소 7pt 미만 축소, 잘림 가능성을 검사 |
| 디자인 | 4.5:1 이상의 텍스트 대비, 템플릿 주색/강조색 분리, 안전 여백, 그리드 정렬, 제목 계층을 검사 |
| 편집성 | PPTX 내부에 편집 가능한 텍스트와 도형 객체가 생성되는지 검증 |

검사 구현은 `src/utils/pptTextLayout.ts`, `src/utils/pptDesignQuality.ts`, `src/utils/pptGrid.ts`, `src/services/pptDocument.service.ts`에 있다.

## 8. 현재 검증 범위와 다음 단계

현재 브라우저 경로에서는 단위 테스트와 DOM 기반 PPTX 출력 검증을 수행한다.

```powershell
npm run lint
npm run test:run
npm run build
```

현재 포함된 테스트는 요청 분석, 목적별 구성, 블루프린트 범위, 섹션 병렬 생성, 언어·중복·누락 검사, 텍스트 맞춤, 그리드·대비·밀도·레이아웃 다양성, PPTX ZIP 내부의 편집 텍스트를 다룬다.

다만 PowerPoint 렌더러별 글꼴 대체, 최종 PDF의 픽셀 단위 충돌, 이미지와 HTML 미리보기의 시각적 차이는 브라우저에서 완벽히 보장할 수 없다. 이 영역은 다음 단계의 독립 QA 워커가 담당한다.

1. LibreOffice로 저장된 PPTX를 PDF/PNG로 렌더링한다.
2. HTML/CSS 기준 화면과 렌더 이미지를 비교한다.
3. 글자 잘림, 겹침, 글꼴 대체, 표·차트 누락, 색상 차이를 품질 리포트로 저장한다.
4. 실패한 결과물은 List에서 다운로드 전에 경고 또는 차단한다.

## 9. 운영 시 확인 지점

- 생성 중 오류는 브라우저 개발자 도구보다 해당 Supabase Edge Function 로그에서 확인한다.
- `OPENAI_API_KEY`는 Supabase Function secret으로만 둔다. Vite 환경변수나 Git에 넣지 않는다.
- 새 기능은 `generate-ppt-deck-blueprint`, `analyze-ppt-request`, `generate-ppt-slide-plan`을 함께 배포해야 한다.
- 화면 미리보기와 PPTX의 레이아웃이 어긋나면 먼저 `PptHtmlSlide.tsx`와 `PptDomExportDeck.tsx`를 확인한다. 일반 PptxGenJS 폴백의 사전검증은 HTML/CSS 디자인 품질의 기준이 아니다.
